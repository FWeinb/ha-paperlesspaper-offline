# Development

Notes for working on the integration itself. For using it, see the
[README](README.md). The architecture and design decisions are in
[docs/DESIGN.md](docs/DESIGN.md), and project terms are in
[GLOSSARY.md](GLOSSARY.md).

## Layout

| Path | Contents |
|---|---|
| `custom_components/paperlessoffline/` | The integration (Python) |
| `frontend/` | Sidebar panel and dashboard card (Lit + TypeScript) |
| `tests/` | `pytest-homeassistant-custom-component` tests |
| `tools/` | Code generators and the hardware check server |
| `docs/` | Design notes |

## Python

```sh
uv venv --python 3.14 && uv pip install -r requirements_test.txt
.venv/bin/pytest -q
.venv/bin/ruff check . && .venv/bin/ruff format --check .
.venv/bin/mypy custom_components
```

`strings.json`, both translation files and `services.yaml` are generated by
`tools/gen_strings.py` and `tools/gen_services_yaml.py`. Edit those scripts,
not the generated files.

## Frontend

The panel and card live in `frontend/`. Vite builds them into
`custom_components/paperlessoffline/frontend/`. That directory is build output:
it is gitignored and must never be edited by hand. Build it to run the
integration from a checkout:

```sh
cd frontend
npm ci
npm run build      # typecheck + bundle
npm run dev        # mock harness at http://localhost:5199 (see dev/mock.ts)
npm run e2e        # interaction smoke test against the running harness
```

Without a build, the integration still loads, but logs a warning and registers
neither the panel nor the card.

The mock harness (`dev/mock.ts`) fakes the integration's websocket API. Query
parameters such as `?frame=kitchen&edit=0`, `?tab=settings`, `?view=card`,
`?dark=1`, `?narrow=1` and `?lang=de` jump to a particular view.

## Local Home Assistant

`tools/ha_dev.py` runs a local Home Assistant with the integration, to try it
end to end. It lives in `.ha-dev/` (gitignored) and links the integration to
the checkout, so it runs the code you are editing.

```sh
.venv/bin/python tools/ha_dev.py           # start; returns once it is up
.venv/bin/python tools/ha_dev.py restart   # after changing Python code
.venv/bin/python tools/ha_dev.py stop
```

It runs in the background at <http://127.0.0.1:8124> (user `dev`, password
`devpass1234`) and logs to `.ha-dev/hass.log`, with the integration at debug
level. The first start creates the instance, skips onboarding and adds a frame
with three sample photos; no real frame is needed. Build the frontend first
(see above); after `npm run build`, reloading the page is enough. Delete
`.ha-dev/` to start over.

## CI

GitHub Actions run on every push and pull request:

- `tests.yml`: ruff, mypy, pytest, and a frontend typecheck and build.
- `validate.yml`: hassfest and HACS validation (also weekly).

## Releases

Publishing a GitHub release runs `release.yml`, which:

1. builds the frontend;
2. sets `version` in `manifest.json` to the release tag (a leading `v` is
   dropped, so `v0.5.0` becomes `0.5.0`);
3. zips the contents of `custom_components/paperlessoffline/` and attaches
   the result to the release as `paperlessoffline.zip`.

HACS installs that zip (`zip_release` in `hacs.json`), so users only ever get
tagged releases. The version bump is not committed back to `main`.

```sh
gh release create v0.5.0 --generate-notes
```

## Screenshots

The README screenshots in `docs/images/` are generated by
`tools/screenshots.py`. It builds the frontend, then starts a throwaway Home
Assistant with three frames, sample photos from
[picsum.photos](https://picsum.photos) and a text card on the living room
frame, simulates a wake for each frame, and takes dark-mode screenshots
with headless Chrome (`tools/screenshots.mjs`). The main panel screenshot
is wrapped in a stylised browser window.

```sh
cd frontend && npm ci && cd ..
.venv/bin/python tools/screenshots.py          # rewrites docs/images/*.webp
.venv/bin/python tools/screenshots.py --keep   # also keeps the HA config to look around
```

It expects Google Chrome in `/Applications`; set `CHROME` to use another
Chromium binary. The frames, photos, card and wake times are defined at the
top of the script.

## Hardware check

`tools/hw_spike.py` serves labelled test patterns to a real frame, to confirm
image encodings and how the panel buffer maps onto the glass. Its docstring
explains the setup. The 13.3" frame is still untested; to check landscape
mounting on one:

```sh
.venv/bin/python tools/hw_spike.py --panel 13 --mount landscape
```

Then report whether the arrow points up.
